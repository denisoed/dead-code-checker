# План реализации

**Plan:** Устранить критичные дефекты в логике детекции dead code, из-за которых инструмент выдаёт ложные срабатывания и пропуски, с приоритетом на корректность CI-режима и стабильность API.

## Data sources / schemas

- Основные входные данные: содержимое файлов, полученное через `getAllFiles` и `readFileContent` (`src/core/fileSystem.ts:9-67`).
- Текущие структуры данных:
  - `deadMap: Record<string, IDeadCodeInfo>` (`src/core/DeadCodeChecker.ts:22`).
  - `exportedSymbols: Set<string>` (`src/core/DeadCodeChecker.ts:25`).
  - `importedSymbols: Map<string, IImportedSymbol[]>` (`src/core/DeadCodeChecker.ts:26`).
- Решение:
  - Ввести внутренний file-scoped key для деклараций (например, `symbolId = filePath + "::" + symbolName`) или эквивалентную структуру, чтобы исключить коллизии одноимённых символов между файлами.
  - Для импортов хранить локальное имя binding и источник отдельно.
- Миграции/индексы: Not required — reason: персистентного хранилища нет, все данные in-memory.

## Contracts and interfaces

- Публичные CLI-контракты (`bin/index.js:21-35`) сохраняются без изменений:
  - `--ci`, `--folder`, `--ignoreNames`, `--ignoreFolders`, `--quiet`, `--no-progress`.
- Публичный API пакета (`src/index.ts:1-3`) сохраняется без breaking changes.
- Внутренние интерфейсы для импортов должны быть расширены так, чтобы различать:
  - исходное имя экспорта,
  - локальный alias/binding в файле-импортёре,
  - факт использования именно локального binding после импорта.
- Формат итогового отчёта (`IDeadCodeReport`) сохраняется совместимым; возможны изменения только в корректности содержимого, не в форме.

## Architecture / Components

### 1. Нормализация модели символов

- Изменить этап сбора деклараций в `src/core/DeadCodeChecker.ts` так, чтобы usage привязывался к конкретной декларации, а не только к `name`.
- Адаптировать логику из `src/core/analysis.ts`:
  - анализировать usage по file-scoped сущности,
  - исключить перекрёстное влияние одноимённых символов из разных файлов.

### 2. Исправление import binding

- Переработать `processImportedNames`/`processCommonJSImports` в `src/core/declarations.ts`:
  - для ESM `import { a as b }` сохранять локальное имя `b` как usage target;
  - для CJS `const local = require('pkg')` и `const local = require('pkg').member` сохранять `local`.
- Обновить проверку использования импортов в `src/core/analysis.ts` и генерацию import-репортов в `src/core/reporting.ts`, чтобы вывод соответствовал реальному local binding.

### 3. Удаление ложного "экспорта" через return-object

- Убрать или строго ограничить `processReturnStatements` (`src/core/declarations.ts:404-414`) в общем pipeline (`src/core/DeadCodeChecker.ts:115`).
- Экспорт должен определяться только ESM/CJS синтаксисом.

### 4. Правило для публичного API export

- Пересмотреть условие в `isDeadCode` (`src/core/analysis.ts:508-520`), где отсутствие внутреннего импорта трактуется как dead code.
- Реализовать безопасную стратегию:
  - по умолчанию не считать export dead code только на основе отсутствия internal import;
  - при необходимости добавить явный строгий режим отдельным флагом (без изменения текущих флагов в рамках этого запроса, если не потребуется).

## Risks

- Риск регрессии отчёта: изменение ключей символов может повлиять на все этапы подсчёта (`usageCount`, `importedIn`, `exportedFrom`).
  - Митигировать через регрессионные fixtures и unit-тесты на каждый критичный сценарий.
- Риск изменения ожиданий пользователей: часть старых "срабатываний" исчезнет после исправления ложноположительных кейсов.
  - Митигировать обновлением README/examples и release notes.
- Риск роста времени анализа на больших проектах.
  - Митигировать замером до/после на фиксированном наборе файлов и отказом от лишних проходов.

## Assumptions

- Фича не требует изменения формата CLI-вывода и не требует новых внешних зависимостей.
- Дополнительные регрессионные примеры можно разместить в существующей тестовой структуре `tests/` и/или `example/`.
- CI в этом проекте запускает `npm test`, поэтому критичные кейсы должны быть автоматизированы на уровне тестов, а не только вручную.
