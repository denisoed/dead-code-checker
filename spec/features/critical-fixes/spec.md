# Критичные исправления точности анализа dead code

**Specification:** Изучить текущую кодовую базу, выявить критичные баги, которые приводят к ложным срабатываниям, пропуску реального dead code или некорректному CI-поведению, и зафиксировать требования к их исправлению.

## User Stories

1. Как инженер CI, я хочу получать корректный `exit code` только при реальных проблемах, чтобы пайплайн не падал из-за ложноположительных детектов.
2. Как разработчик библиотеки, я хочу чтобы экспортируемый публичный API не помечался как dead code только потому, что он не используется внутри того же репозитория.
3. Как разработчик TypeScript/JavaScript проекта, я хочу корректную обработку alias-import и CommonJS-import, чтобы отчёт по неиспользуемым импортам был достоверным.
4. Как владелец большого монорепозитория, я хочу независимый учёт одноимённых символов в разных файлах, чтобы использование `helper` в одном модуле не скрывало неиспользуемый `helper` в другом.

## Main scenarios and rules

### Сценарий 1: Коллизия имён между файлами

- **Факт (evidence):** агрегатор `deadMap` индексируется только по `name`, без ключа файла (`src/core/DeadCodeChecker.ts:22`, `src/core/DeadCodeChecker.ts:94-109`).
- **Факт (evidence):** анализ usage выполняется по множеству имён без file-scoped identity (`src/core/analysis.ts:410-447`).
- **Риск:** использование символа с тем же именем в другом файле может маскировать реальный dead code.
- **Правило:** идентификатор анализируемого символа должен быть уникален минимум по паре `(filePath, symbolName)` для деклараций; использование должно рассчитываться на уровне конкретной декларации.

### Сценарий 2: Некорректная обработка alias import

- **Факт (evidence):** при `import { a as b }` сохраняется `a`, а не локальное имя `b` (`src/core/declarations.ts:373-377`).
- **Риск:** импорт может быть фактически использован через alias, но будет помечен как "imported but not used".
- **Правило:** для `as` нужно хранить и анализировать локальное имя, которое реально используется в файле-импортёре.

### Сценарий 3: Некорректная обработка CommonJS direct import

- **Факт (evidence):** `const x = require('pkg')` не учитывается вовсе (ветка работает только при наличии `match[3]`) (`src/core/declarations.ts:331-336`).
- **Факт (evidence):** в `const local = require('pkg').member` сохраняется `member`, а не `local` (`src/core/declarations.ts:333-335`).
- **Риск:** пропуск реальных неиспользуемых import либо ложные отчёты для корректного кода.
- **Правило:** для CommonJS нужно отслеживать локальное связанное имя, а не имя свойства источника.

### Сценарий 4: `return { ... }` ошибочно учитывается как экспорт модуля

- **Факт (evidence):** любые свойства из `return { ... }` добавляются в `exportedSymbols` (`src/core/declarations.ts:404-414`, вызов в `src/core/DeadCodeChecker.ts:115`).
- **Риск:** локальные переменные, возвращённые из функции, могут ошибочно считаться экспортированными и пропускаться как dead code.
- **Правило:** module export должен определяться только через синтаксис экспорта/импорта модуля (ESM/CJS), а не через `return` внутри функции.

### Сценарий 5: Ложное определение dead code для публичных export

- **Факт (evidence):** экспортированный символ считается dead code, если не импортирован внутри сканируемой области, кроме PascalCase-исключения (`src/core/analysis.ts:508-520`).
- **Риск:** валидный публичный API библиотек ошибочно детектируется как dead code и ломает CI.
- **Правило:** отсутствие внутреннего импорта не является достаточным признаком dead code для экспортированного API; нужен отдельный режим/правило (например, opt-in строгий режим или иной критерий).

## Non-functional requirements

- Точность: после исправлений критичных сценариев отчёт не должен содержать ложноположительных результатов по alias import, CommonJS local binding и публичным export в подготовленных регрессионных кейсах.
- Предсказуемость CI: `--ci` должен завершаться кодом `1` только при реальном наличии элементов в финальном отчёте.
- Стабильность: изменения не должны ломать текущую поддержку форматов файлов из `DEFAULT_EXTENSIONS` (`src/config.ts:17-30`).
- Производительность: изменение модели ключей символов не должно приводить к деградации анализа более чем на 20% на тестовом наборе feature fixtures.

## Assumptions

- Критичным считается баг, который нарушает корректность отчёта (false positive/false negative) или влияет на надёжность CI-проверки.
- В текущем запросе scope ограничен подготовкой спецификации и плана исправлений; внедрение фиксов стартует отдельным запросом на выполнение `spec/features/critical-fixes/tasks.md`.
- Обратная совместимость CLI-опций обязательна (текущие флаги в `bin/index.js:21-35`).
